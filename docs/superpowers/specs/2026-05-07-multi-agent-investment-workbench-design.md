# 多智能体投资决策工作台设计

## 目标

新增一个独立的多智能体投资决策工作台，用于对 ETF 单品、账户组合和通用投资问题进行多视角分析、辩论与裁决。工作台的核心要求是：每个角色都必须真实调用 LLM 参与推理，先并行初评，再进行多轮辩论，最后由裁决角色收敛成统一结论。

这套工作台必须满足以下要求：

- 作为独立入口存在，不干扰现有单智能体助手、持仓建议、账户分析流程。
- 默认接入现有持仓、账户上下文和搜索能力。
- 支持三个场景：ETF、账户、通用问答。
- 每个场景支持最大辩论轮数设置，默认值由产品定义，用户可在页面调整。
- 结果风格保持平衡型：允许分歧，但最终必须收敛到一个可执行结论或明确的观望结论。
- 输出必须可追溯：结论、分歧、证据来源、搜索结果都要能回放。

## 非目标

以下内容不在本次范围内：

- 不改造现有单智能体助手为多智能体模式。
- 不把多智能体结果直接写入交易执行链路。
- 不引入人为“投票娱乐化”流程，所有角色输出必须受证据约束。
- 不追求固定角色模板覆盖所有场景。
- 不允许单轮静态模板直接伪装成多智能体辩论，所有角色都必须进入 LLM 推理链路。

## 总体方案

采用“独立工作台 + 场景驱动角色生成 + LLM 并行初评 + 多轮辩论 + 裁决智能体”的架构。

工作台入口独立于现有助手，进入后先选择场景，再由后端生成与该场景匹配的角色集合。第一轮各角色并行调用 LLM 完成初评，随后进入多轮辩论流程：角色会看到上一轮的反对意见、争议摘要和必要的新增搜索结果，再次调用 LLM 修正观点；裁决角色在每轮检查是否已满足收敛条件，并在达到一致或达到最大轮数时输出最终裁定。

该方案的核心原则是：

1. 场景优先于角色模板。ETF、账户、通用三类场景使用不同角色组合。
2. 证据优先于措辞。角色输出必须绑定上下文和搜索结果。
3. 决策优先于表演。多智能体的目的不是展示“谁说得更像”，而是得出可执行结论。
4. 保守优先于误判。证据不足时必须降级，不允许硬给强结论。
5. 收敛优先于轮数。只要裁决角色判断分歧已可忽略且没有强烈反对意见，就应停止继续辩论。

## 架构

### 前端

新增一个独立页面作为多智能体工作台入口。

页面包含：

- 场景选择器：ETF / 账户 / 通用。
- 上下文摘要区：展示当前可用持仓、账户和搜索上下文。
- 角色分析区：展示各智能体观点、证据与反方质疑。
- 裁决结论区：展示最终共识、建议动作、置信度和风险说明。
- 来源区：展示搜索结果、引用依据、上下文来源。

### 后端

新增一条与现有 `AdvisorService`、`AssistantService` 分离的多智能体决策管线。

后端流程分为五层：

1. 场景识别与上下文组装。
2. 角色并行初评。
3. 多轮交叉质疑与辩论。
4. 裁决智能体判断收敛条件。
5. 裁决智能体输出最终结论并落库。

角色不固定为全局统一模板，而是根据场景动态生成。

## 场景设计

### ETF 场景

适用于单只 ETF 的买入、持有、加仓、减仓、卖出判断。

建议动态角色：

- 事件与政策角色：分析最新公告、行业政策、宏观事件对该 ETF 的方向影响。
- 技术面角色：分析趋势、均线、超买超卖和短期节奏。
- 基本面/配置角色：分析该 ETF 的中长期配置价值。
- 风控裁决角色：识别追高、回撤、政策冲击、过度集中等风险。

### 账户场景

适用于整体组合仓位、资产配置、再平衡和风险暴露分析。

建议动态角色：

- 组合结构角色：分析资产分布、集中度、现金比例和相关性。
- 再平衡角色：分析是否需要调仓、分散或降低单一方向暴露。
- 风险暴露角色：识别行业、风格、市场和宏观因子集中风险。
- 执行与资金角色：关注可用资金、分批调仓节奏和执行成本。

### 通用场景

适用于用户对投资问题、市场观点、ETF 选择、宏观研判的自然语言提问。

建议动态角色：

- 研究员角色：给出主分析结论。
- 反方质疑角色：专门寻找逻辑漏洞、过度乐观或过度悲观的问题。
- 搜索证据角色：负责收集最新新闻、政策、公告和宏观事件。
- 风控裁决角色：将分歧收敛成可执行的保守或中性结论。

## 数据流

### 输入

用户进入工作台后输入或选择：

- 场景：ETF / 账户 / 通用。
- 目标对象：具体 ETF、账户组合或自然语言问题。
- 可选限制：是否缩小到某个仓位、时间区间或重点品种。

系统自动读取的上下文包括：

- ETF 场景：持仓明细、最新行情、历史 K 线、技术指标、搜索结果。
- 账户场景：账户总金额、可用现金、持仓分布、集中度、最新搜索结果。
- 通用场景：用户问题、可选账户上下文、可用市场搜索结果。

### 中间过程

1. 场景路由器根据输入生成角色集合和最大辩论轮数。
2. 第一轮中，每个角色独立调用 LLM 并输出结构化初评。
3. 编排器聚合第一轮结果，提炼争议摘要和强反对意见。
4. 第二轮及之后，每个角色都带着“上一轮自我观点 + 他人反驳摘要 + 新搜索结果”再次调用 LLM。
5. 裁决角色在每轮结束时判断是否满足收敛条件：分歧已可忽略且没有强烈反对意见。
6. 若未收敛且未达到最大轮数，则继续下一轮辩论；若达到收敛或达到最大轮数，则输出最终结论。

### 输出

最终输出必须包含：

- 最终结论。
- 推荐动作。
- 置信度。
- 支撑证据。
- 分歧点。
- 风险说明。
- 来源质量。
- 辩论轮次与每轮概要，供前端默认折叠展示。

## 结果规范

多智能体工作台的最终结果采用平衡型规则：

- 若多个角色对方向一致，输出明确动作。
- 若存在明显分歧，允许输出 `hold`、`wait`、`reduce exposure` 等保守结论。
- 若搜索结果不足或来源质量偏低，必须降级，不允许强行给出高置信度动作。
- 裁决角色必须说明为什么没有达成更强共识。
- 默认最大辩论轮数由前端设置，但后端必须有安全上限，防止无限辩论。

建议结果字段如下：

- `final_conclusion`
- `recommended_action`
- `confidence`
- `supporting_evidence`
- `disagreements`
- `risk_notes`
- `source_quality`
- `debate_rounds`
- `round_summaries`
- `role_opinions_by_round`

## 前端交互

工作台页面建议采用以下布局：

- 顶部：场景选择和输入区。
- 中部：多智能体分析卡片列表，按角色展示观点与质疑。
- 右侧或底部：证据来源和搜索结果。
- 底部：裁决结论固定展示。
- 完整辩论过程默认折叠，用户手动展开后可以查看每轮每个角色的原始观点、反驳摘要和裁决变化。
- 页面提供“最大辩论轮数”设置项。

前端不应复用现有单智能体助手界面，以免用户混淆“普通问答”和“多智能体研判”两种流程。

## 后端接口建议

建议新增独立接口，不与现有助手接口混用。

可能的接口形态：

- `POST /api/multi-agent/analyze`
- `GET /api/multi-agent/history`
- `GET /api/multi-agent/history/{id}`

请求体至少包含：

- `scenario`
- `query`
- `target_etf_code` 或 `portfolio_id`
- `include_portfolio_context`
- `include_account_context`
- `search_enabled`
- `max_debate_rounds`

返回体至少包含：

- `scenario`
- `roles`
- `debate`
- `final_conclusion`
- `created_at`
- `source_summary`
- `max_debate_rounds`
- `actual_debate_rounds`

## 搜索与上下文策略

多智能体工作台默认接入现有搜索能力，但应遵循以下策略：

- ETF 场景优先搜索与该品种直接相关的公告、政策、行业新闻和宏观事件。
- 账户场景优先搜索影响组合主要暴露因子的最新事件。
- 通用场景优先围绕用户问题和高相关投资主题搜索。
- 搜索结果不足时，裁决角色必须显式标记信息不足。
- 搜索结果必须区分 `direct / indirect / weak` 相关性，不能把弱相关事件当作主要结论依据。
- 每一轮辩论都允许角色重新搜索，但应优先复用已有上下文，避免无意义重复检索。

## 风险与约束

1. 不可将多智能体结果直接作为交易执行指令。
2. 不可让裁决角色忽略风控角色的高风险警告。
3. 不可把搜索失败包装成明确利好或利空。
4. 不可使用固定角色模板覆盖所有场景，场景差异必须体现在角色提示词中。
5. 不可让前端与现有助手共享同一视觉路径，避免用户误解。
6. 不可无限辩论，必须支持最大轮数和收敛判定。

## 测试策略

最低需要覆盖以下测试：

- 场景路由测试：ETF、账户、通用是否生成正确角色集合。
- 搜索降级测试：搜索结果为空时是否输出保守结论。
- 冲突裁决测试：角色分歧较大时是否避免输出强烈动作。
- 结果结构测试：最终响应是否包含规定字段。
- 回放测试：相同输入是否能复现相同结构化输出。

## 逐步落地建议

建议按以下顺序实现：

1. 先实现后端多智能体管线和统一结果结构。
2. 再实现独立工作台页面和基础展示。
3. 然后补历史记录与回放。
4. 最后再优化角色辩论细节和视觉呈现。

这能保证功能先可用，再迭代深化，不会一开始就把系统做得过重。
